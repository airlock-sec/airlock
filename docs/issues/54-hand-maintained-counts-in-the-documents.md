> **Repo context.** `airlock` is a Python 3.11 standard-library-only scanner: `src/airlock/` holds the pipeline (collector, then rules and detectors, then fingerprints and suppressions, then reporters) behind one CLI, and the rules themselves are data in `rules/builtin/*.toml`. The repository being scanned is untrusted input, so the hard rules in [`AGENTS.md`](https://github.com/airlock-sec/airlock/blob/main/AGENTS.md) section 4 are security properties rather than style. [`ROADMAP.md`](https://github.com/airlock-sec/airlock/blob/main/ROADMAP.md) is the source of truth for what is built and what is only a docstring.

> 🟢 **Unblocked.** `scripts/build_site.py` already derives the site's counts from rule data (lines 218-234), `ROADMAP.md`'s progress table is generated by 1.9 and 1.15, and pytest reports the test count, so every number involved is computable today.

## Problem

`README.md:30` and `docs/wave/application.md:46` both state a rule count and a test count as prose. `docs/wave/settings.md:167` states a readiness percentage and `:190` a rule count. `ROADMAP.md`'s generated table is the source for readiness, and `rules/builtin/*.toml` is the source for rules; nothing is the source for the test count, because no document is allowed to disagree with the suite it describes.

The drift is visible now: `docs/wave/settings.md:190` says twenty-two rules ship while 24 do, and `:167` says 36% readiness against the generated row. 1.15's own record ends by noting that "the counts in README and `docs/wave/application.md` are hand-maintained prose that a merge still resolves by hand", which is a known problem with no task against it.

`README.md`'s four rule tables (lines 62-111) duplicate the severities that `rules/builtin/*.toml` declares, so a severity change is two edits in different languages, one of which no test reads.

## What to build

1. **Pick one owner per number.** Readiness comes from the generated table, rule counts from the rule files, the test count from a collection run (or is deleted, which is the honest option for a number that changes weekly). Say which, in each document.
2. **Generate or verify.** Either extend `scripts/build_site.py`'s approach with a region in `README.md` that a script rewrites, the way `ROADMAP.md`'s three regions work, or add a test that refuses a stated count disagreeing with the data. A verified hand-written number is cheaper and stays reviewable.
3. **Take the rule tables out of `README.md`** if the generated reference and the site already carry them, leaving a link and the four families' purpose rather than 24 rows of severity a merge can forget to update. The open issue #29 owns the generated rule reference, so coordinate by stating in the record which table source each document ends up using.
4. **Fix the currently wrong numbers** in the same change, listing which was checked against which source.

**Out of scope:** Building the generated rule reference itself (the open issue #29), and any change to what the readiness table counts.

## Acceptance criteria

- [ ] Every count in a document is either generated from a source or asserted against one by a test.
- [ ] The rule counts, readiness percentage and test count in `README.md`, `docs/wave/settings.md` and `docs/wave/application.md` agree with the data at the time of the merge.
- [ ] `README.md`'s severity tables either carry the generated values or are replaced by a link to the generated reference, with the reason recorded.
- [ ] A future rule-severity change cannot leave a stale table behind without a failing check.
- [ ] A change record with a UTC date exists under `docs/changes/`, `ROADMAP.md` has been regenerated from it, and `python scripts/roadmap_progress.py --check` passes.
- [ ] `python -m pytest`, `ruff check .`, `ruff format --check .` and `mypy src` all pass on Linux, and `airlock scan --mode full .` reports no HIGH findings.
- [ ] PR description includes `Closes #{{issue:self}}`.
