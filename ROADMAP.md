## 0. The update rule (mandatory)

**Every contribution updates this file in the same pull request.** That covers code, rules, tests, docs, CI, configuration, dependency bumps and reverts, by humans and by agents. No exceptions.

Each PR must:

1. **Tick, untick or add tasks.** Change `[ ]` to `[x]` only when the task's "Done when" is true. Add a new task (with the next free ID in its phase) for any work discovered along the way.
2. **Add one change record** under `docs/changes/`: a file named `YYYY-MM-DD-HHMM-<slug>.md` for the UTC minute the change landed, with `date:`, `tasks:` and `summary:` front matter and the record itself below it. Section 9 says what each part means.
3. **Regenerate this file** with `python scripts/roadmap_progress.py`. It rebuilds the progress table from the task lines, the changelog in section 9 from the records, and `Last updated` from the newest record. Those three are generated; do not hand-edit them.
4. **Update the decision log** (section 7) if a decision was made, and the risk register (section 8) if a risk changed.

Enforcement: `roadmap-check.yml` runs `scripts/check_roadmap_touched.sh`, which fails a PR that
changes files without *adding* a record, without the regenerated copy of this file, or that removes
a record already on the base branch, and `python scripts/roadmap_progress.py --check`, which fails
any generated region that disagrees with its source, including the `Last updated` line. The PR
template carries a checkbox for the same rule, and reviewers enforce it by hand until the workflow
is a required check (1.3). A PR whose only file is this one is a planning edit and is always
allowed. This rule is repeated in `PRD.md` (14), `ARCHITECTURE.md` (17),
`ARCHITECTURE_ESSENTIALS.md` (0), `project_structure.md`, `AGENTS.md`, `CLAUDE.md`,
`CONTRIBUTING.md` and the PR template.

Conventions: sizes are relative effort, not calendar time (S under a couple of hours, M about half a day, L one to two days, XL several days). They are unmeasured guesses. "Deps" lists task IDs that must be done first. Task IDs are stable: never renumber, never reuse.

## 9. Changelog

Newest first, one row per change. This block is generated: its source is the files under
`docs/changes/`, and `python scripts/roadmap_progress.py` renders one row per file, ordered by the
date and time in the name, with the slug breaking a tie when two changes landed in the same minute.

A record is one file, named `YYYY-MM-DD-HHMM-<slug>.md` in UTC, holding three front matter keys and
the record itself:

```markdown
---
date: 2026-10-30 15:52 UTC
tasks: 7.2, FR-20
summary: What changed, in one sentence, as it should read in the table below.
---

What the change does, why it was needed, what was verified, and what it does not cover.
```

The `summary:` is the table cell, so it stays under 240 characters and writes any `|` as `\|`; a
lone `|` or a stray `\` in it is refused. The `date:` must match the name, must not be in the
future, and the file sits directly in `docs/changes/` rather than in a subdirectory, because the
render does not recurse. The record body is what a reviewer reads when the row is not enough.
One file per change is the point: two changes never touch the same path, so a changelog conflict
between two branches is resolved by keeping both files and running the generator again. Once a
record has landed on the default branch it is not deleted or renamed (the gate refuses a record
that disappears), so a wrong record is corrected by a later one. The rows before 2026-10-30 were
migrated by a script from the table this section used to hold: each record body contains its old
row verbatim, and each `summary:` is that row kept whole (2 of 36), that row's opening cut at a
word boundary (27), or a sentence written by hand (7, where the first sentence described the change
badly). The newest-first order is the generator's: three records that carry only a date now order
by slug, and one pair the hand-written table had the wrong way round is now correct.
